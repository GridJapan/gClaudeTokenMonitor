# ログ形式リファレンス

`ctm record` が書き出す記録の完全な仕様。**別プロセス（別の Claude セッションを含む）が
ここを読んでトークン消費を確認する**ことを想定して書いてある。

最終更新: 2026-08-22

---

## 1. 場所と一覧

既定の記録先は `~/.ctm/`（`ctm record -out <dir>` で変更可能）。

```
~/.ctm/
├── events/
│   └── 2026-08-22.ndjson    メッセージ明細（機械可読・本書 §2）
├── daily/
│   └── 2026-08-22.md        同じ内容の人間可読表
├── limits/
│   ├── 2026-08-22.ndjson    プラン使用率サンプル（機械可読・本書 §3）
│   └── 2026-08-22.md        同じ内容の人間可読表
├── state.json               レコーダーの読み取り位置（§5）
├── record.lock              稼働中レコーダーのハートビート（§5）
├── record.log               レコーダー自身の動作ログ
└── ui.json                  CtmMonitor の表示設定（ログではない）
```

ファイルは**日付でローテート**する。日付はメッセージのタイムスタンプ（ローカル時刻）の日付。

## 2. events/YYYY-MM-DD.ndjson — メッセージ明細

**1 行 = 重複排除後の課金単位 1 件**（用語は `用語統一表.md` の「メッセージ」）。
追記専用。行は当日分の中でタイムスタンプ昇順。

### 行の例

```json
{"ts":"2026-08-22T01:42:50+09:00","key":"msg_01ABC...|req_01XYZ...","session":"1a2b3c4d-....","cwd_name":"my-project","model":"claude-opus-5","input":2,"cache_write_5m":0,"cache_write_1h":273148,"cache_read":0,"output":1019,"total":274169,"cost_usd":2.756965,"priced":true}
```

### フィールド

| フィールド | 型 | 意味 |
|---|---|---|
| `ts` | string (RFC3339) | メッセージのタイムスタンプ。ローカルタイムゾーン付き |
| `key` | string | 重複排除キー `message.id + "\|" + requestId`。**全期間で一意** |
| `session` | string | セッション ID（UUID）。Claude Code のログファイル名と同一 |
| `cwd_name` | string | 作業ディレクトリ（`cwd` の末尾フォルダ名） |
| `model` | string | 正規化済みモデル ID（例 `claude-opus-5`。ベンダー接頭辞・日付サフィックスは除去済み） |
| `input` | int | 新規入力トークン |
| `cache_write_5m` | int | 5 分キャッシュへの書き込みトークン |
| `cache_write_1h` | int | 1 時間キャッシュへの書き込みトークン |
| `cache_read` | int | キャッシュ読み出しトークン |
| `output` | int | 出力トークン |
| `total` | int | 上記 5 種の合計 |
| `cost_usd` | float | リスト価格換算のコスト（§7 参照） |
| `priced` | bool | `false` なら未知モデルでコスト 0 として記録されている |

### 保証されること

- **重複なし**: 同じ `key` の行は 1 本しか書かれない。Claude Code の生ログは同一応答を
  複数行書くが、その水増し（実測 1.7 倍）は除去済み
- **純 ASCII**: 非 ASCII 文字は `\uXXXX` エスケープ。どのコードページのコンソールを
  経由しても壊れない。`cwd_name` の日本語はデコードすると復元される
- **追記専用**: 既存行は書き換えられない。ファイル末尾だけ監視すればよい
- **`<synthetic>` モデルと usage ゼロの行は含まれない**

### 集計のしかた

- ある期間の消費 = `ts` でフィルタして `total` / `cost_usd` を合計するだけ（重複排除済みなので）
- セッション別 = `session` でグループ化
- 5 種のトークンは料金レートが違う（§7）。**トークン数の単純合算で費用を語らない**こと

## 3. limits/YYYY-MM-DD.ndjson — プラン使用率サンプル

**1 行 = 1 つの制限枠の 1 回の観測**。既定で 5 分ごとに、Anthropic の公式 API から取得した
使用率と、同じ窓で ctm が実測した消費を**同じ行に**記録する。

### 行の例

```json
{"ts":"2026-08-22T15:15:06+09:00","key":"weekly-fable","label":"週次・Fable","percent":2,"severity":"normal","resets_at":"2026-08-26T16:59:59.988752+00:00","is_active":false,"window_start":"2026-08-20T01:59:59+09:00","messages":1,"tokens":489290,"cost_usd":9.824539,"implied_limit_tokens":24464500,"implied_limit_cost_usd":491.226}
```

### フィールド

| フィールド | 型 | 意味 |
|---|---|---|
| `ts` | string | 観測時刻 |
| `key` | string | 枠の識別子: `session`（5時間制限）/ `weekly_all`（週間・全モデル）/ `weekly-<モデル名>`（モデル別週次） |
| `label` | string | UI と同じ表示名（`5時間制限` など） |
| `percent` | float | **公式の使用率（%）**。Claude Code の画面に出る値と同じソース |
| `severity` | string | API が返す深刻度（`normal` など） |
| `resets_at` | string | この枠がリセットされる時刻（UTC） |
| `is_active` | bool | API がこの枠を「現在の制限要因」と見なしているか |
| `window_start` | string | 窓の開始時刻（`resets_at` から逆算。session=5h、weekly=168h） |
| `messages` | int | 窓内で ctm が実測したメッセージ数 |
| `tokens` | int | 同・合計トークン |
| `cost_usd` | float | 同・コスト |
| `implied_limit_tokens` | int | `tokens / (percent/100)`。この観測から逆算した窓の容量 |
| `implied_limit_cost_usd` | float | 同・コスト換算 |

### 使いどころ

- **残り何 % か** → 該当 `key` の最新行の `percent`
- **1% あたり何トークンか** → `implied_limit_tokens / 100`
- **ポーリングの合間の推定** → 最新の `implied_limit_cost_usd` と、events の直近合計から補間
- 取得失敗時（レート制限・オフライン）は**行が増えない**だけ。欠測は異常ではない

## 4. daily/*.md と limits/*.md

同じ内容の Markdown 表。人間が直接開く用で、機械処理には §2 §3 の ndjson を使うこと。
列構成はファイル冒頭のヘッダ行に書いてある。

---

## 5. 運用ファイル

| ファイル | 内容 |
|---|---|
| `state.json` | 各セッションログのバイトオフセット。`{"offsets": {"<path>": <int>}, "updated": ..., "version": ...}`。レコーダーの再開位置であり、他プロセスが使う必要はない |
| `record.lock` | `{"pid": int, "heartbeat": RFC3339, "dir": str, "interval_sec": int}`。**heartbeat が `3 × interval_sec`（下限 3 分）以内なら稼働中**。レコーダーが生きているかの判定はこれを読む |
| `record.log` | レコーダーの起動・停止・エラー。1 行 1 イベントのプレーンテキスト |
| `record.stop` | 停止要求。これを置くとレコーダーが次の tick で正常終了する（`ctm stop` が使う） |

## 6. 別プロセスからの読み方

### 推奨: ctm CLI を使う（パースが不要）

```bash
# 現在の全体集計（JSON・純 ASCII）
ctm show -json

# 期間を切り出して集計（実稼働時間・中断コスト検出つき）
ctm query -from "13:00"
ctm query -from "2026-08-22 01:38" -session 1a2b3c4d

# メッセージ明細を NDJSON で（アーカイブではなく生ログから直接）
ctm events -since "13:00"

# プラン使用率の当日履歴
ctm limits history
```

`ctm query` は §2 のアーカイブを読む。`ctm show` / `ctm events` は Claude Code の生ログを
直接読む（アーカイブ非依存・重複排除は同じ）。

### 生ファイルを直接読む場合の注意

1. **共有モードで開く**こと。レコーダーが書き込み用に掴んでいるため、排他で開くと
   Windows では `IOException` になる
   - PowerShell: `[IO.File]::Open($p,'Open','Read','ReadWrite,Delete')`
   - Python: 通常の `open()` で可（共有既定）
   - C#: `new FileStream(p, FileMode.Open, FileAccess.Read, FileShare.ReadWrite | FileShare.Delete)`
2. **最終行が書きかけの可能性**は実質ない（レコーダーは tick 単位でフラッシュする）が、
   JSON パース失敗行は捨てて先へ進むのが安全
3. **末尾追記だけを追う**なら、読んだバイト位置を覚えて `seek` すればよい。
   行は追記のみ・並べ替えなし
4. 日付をまたぐ処理は、前日と当日の 2 ファイルを見る

### Python の最小例

```python
import json, os, glob
d = os.path.expanduser("~/.ctm/events")
tok = cost = 0
for p in glob.glob(os.path.join(d, "*.ndjson")):
    for line in open(p, encoding="ascii"):
        try:
            e = json.loads(line)
        except ValueError:
            continue
        tok += e["total"]; cost += e["cost_usd"]
print(tok, cost)
```

### PowerShell の最小例

```powershell
$e = Get-Content "$env:USERPROFILE\.ctm\events\$(Get-Date -Format yyyy-MM-dd).ndjson" |
     ForEach-Object { $_ | ConvertFrom-Json }
"{0:N0} tok  {1:N2} USD" -f ($e | Measure-Object total -Sum).Sum, ($e | Measure-Object cost_usd -Sum).Sum
```

## 7. コストの意味と制約

- `cost_usd` は **Anthropic の公開リスト価格による換算値**。定額プラン（Pro / Max）では
  実請求は発生しない。「API 従量課金ならいくら相当か」の目安
- レートは input を 1.0x として: cache-write 5m = 1.25x / cache-write 1h = **2.0x** /
  cache-read = **0.1x** / output は別単価。**同じ 100 万トークンでも種別で費用が 20 倍違う**
- `priced: false` の行は料金表に無いモデルで、コスト 0 として計上されている
- プラン使用率（%）の**唯一の公式ソースは §3 の `percent`**。events から % は導出できない
  （窓の容量が非公開のため）
