# ctm システム構成

図を起こす前提の説明。**箱・矢印・境界線**が識別できるように書いてある。

---

## 1. いちばん大事な設計思想：計測対象に触れない

ctm は計測対象に一切手を入れない。Claude Code が**自分の都合で書いているログ**を、外から読むだけ。

```
┌─ 計測対象（何も知らない）──────────┐        ┌─ 計測側 ─────────────┐
│  Claude Code セッション A          │        │                      │
│  Claude Code セッション B          │ ──書── │  ~/.claude/projects  │ ──読── ctm
│  Claude Code セッション C          │        │  （OS のファイル）    │
└────────────────────────────────────┘        └──────────────────────┘
        ↑ ctm を知らない・設定不要                    ↑ 一方通行
```

**矢印は必ず片方向**。ctm からセッションへ戻る線は無い。これが「観測者効果ゼロ」の根拠で、
計測手順を対象の中に書く方式（＝自己計測）との決定的な差になる。

---

## 2. 全体像（3 層）

```
[層1] データ源      ~/.claude/projects/<エンコードされたcwd>/<sessionId>.jsonl
                     │  Claude Code が追記し続ける。全セッションぶん。
                     ▼
[層2] 取り込み      scanner → parser → pricing → store
                     │  差分読み・重複排除・料金計算
                     ▼
[層3] 出力          live / show / events / record / query
```

---

## 3. コンポーネント（箱にする単位）

| 箱 | ファイル | 役割 | 入力 → 出力 |
|---|---|---|---|
| **Scanner** | `scanner.go` | 全 jsonl を走査し、追記分だけ読む | ディレクトリ → 行 |
| **Parser** | `parser.go` | 1 行を Entry に変換。重複キーを作る | 行 → Entry + key |
| **Pricing** | `pricing.go` | 種別ごとのレートで金額を出す | Usage → コスト |
| **Store** | `store.go` | 重複排除して集計。5h ブロック・スナップショット | Entry → 集計 |
| **Recorder** | `record.go` | 常駐してアーカイブに追記 | Entry → NDJSON + md |
| **Query** | `query.go` | アーカイブから期間を切り出す | 期間 → 集計 |
| **Render** | `render.go` | TUI 描画 | 集計 → 画面 |
| **CLI** | `main.go` | サブコマンド振り分け | 引数 → 実行 |

---

## 4. データフロー（矢印にする単位）

### 4.1 取り込みの流れ（共通）

```
jsonl の行
   │
   ├─ "usage" を含まない ────────────────→ 捨てる
   ├─ type != "assistant" ───────────────→ 捨てる
   ├─ model が "<synthetic>" ────────────→ 捨てる
   ├─ usage が全ゼロ ────────────────────→ 捨てる
   │
   ▼
Entry を作る（時刻・セッション・cwd名・モデル・トークン5種）
   │
   ▼
key = message.id + "|" + requestId
   │
   ├─ 既出 ──────────────────────────────→ 捨てる（★重複排除）
   │
   ▼
Pricing でコストを付ける
   │
   ▼
Store / Recorder へ
```

**★重複排除が図の要**。Claude Code は 1 つの応答を `requestId` 単位で複数行書くため、
これを飛ばすと **1.7 倍**に膨らむ（実測: 232 メッセージが 397 に、$69 が $138 に）。

### 4.2 差分読み

```
ファイルごとにバイトオフセットを保持
   │
   ├─ サイズ == オフセット ──→ 読まない
   ├─ サイズ  < オフセット ──→ 切り詰められた。0 から読み直す
   └─ サイズ  > オフセット ──→ 差分だけ読む
                                 └─ 改行で終わっていない行は次回に持ち越す
```

## 5. 実行モード（5 つの出口）

```
                    ┌──────────────┐
                    │  ctm (CLI)   │
                    └──────┬───────┘
        ┌──────────┬───────┼────────┬──────────┐
        ▼          ▼       ▼        ▼          ▼
     live       show    events   record     query
   （TUI）    （1回）  （明細）  （常駐）  （切り出し）
        │          │       │        │          │
        └──────────┴───────┘        │          │
             都度スキャン            │          │
                                     ▼          ▲
                              ~/.ctm アーカイブ ┘
```

- `live` / `show` / `events` は**その場でログを読み直す**。常駐と独立に動く
- `record` だけがアーカイブに**書く**
- `query` はアーカイブを**読む**だけ。ログには触らない

---

## 6. 常駐レコーダーの中身（`ctm record`）

```
起動
 │
 ├─ record.lock を見る
 │    ├─ 3 間隔より新しい ──→ 起動しない（★二重記録の防止）
 │    └─ 古い / 無い ────────→ 引き継ぐ
 │
 ├─ state.json からオフセットを復元  ★再起動しても続きから
 ├─ 直近 2 日のアーカイブから重複キーを復元
 │
 ▼
┌─ 20 秒ごとのループ ────────────────────────┐
│  record.stop がある？ ──→ フラッシュして終了 │
│  差分を読む → 重複排除 → 時刻順に並べる      │
│  events/<日付>.ndjson へ追記                 │
│  daily/<日付>.md へ追記                      │
│  フラッシュ → state.json 更新 → lock 更新    │
└──────────────────────────────────────────────┘
```

**順序が重要**：フラッシュが成功してからオフセットを進める。逆にすると
クラッシュ時に取りこぼす。図では「flush → saveState」の順を明示すること。

### 保存先

```
~/.ctm/
├── events/2026-08-22.ndjson   機械可読・1 メッセージ 1 行・日付ローテート
├── daily/2026-08-22.md        人が読む表
├── state.json                 各ログの読み取り位置（原子的に書き換え）
├── record.lock                稼働中プロセスのハートビート
└── record.log                 レコーダー自身のログ
```

---

## 7. 状態と制御（外から触る点）

```
   ctm status ──読──→ record.lock / state.json / events    （プロセスに触らない）
   ctm stop   ──書──→ record.stop  ──→ レコーダーが次の tick で気づいて正常終了
```

`kill` と違い、バッファのフラッシュとロック解放を済ませてから終わる。
ハートビートが 3 分以上止まっていれば `status` が「応答なし」を出す。

## 8. 計測の時系列（シーケンス図にする部分）

```
ログオン
  │
  ├─ スタートアップ ──→ ctm-record.vbs ──→ ctm record -quiet（常駐開始）
  │
  ├─ ユーザーが Claude Code を起動（何個でも）
  │     └─ セッションが勝手にログを書く
  │            └─ レコーダーが 20 秒ごとに拾う
  │
  ├─ 作業する（計測を意識しない）
  │
  └─ あとで  ctm query -from "13:00" -session <ID>
                 └─ アーカイブから期間を切り出して集計
```

**準備フェーズが無い**のが要点。「測ろう」と思った時点で既に記録済み。

## 9. コスト計算（レートの差を図に）

USD / 100 万トークン。input を基準に倍率が付く。

| 種別 | 倍率 | 意味 |
|---|---|---|
| input | 1.0x | 新規入力 |
| cache-write 5m | 1.25x | 5 分キャッシュへ書く |
| cache-write 1h | **2.0x** | 1 時間キャッシュへ書く |
| cache-read | **0.1x** | キャッシュから読む |
| output | 別レート | 生成 |

**20 倍の開きがある**ので、トークン数の合算では費用を語れない。実測例：

| 種別 | トークン量シェア | コストシェア |
|---|---:|---:|
| cache-write 1h | 2.8% | **33.2%** |
| cache-read | **96.8%** | 57.1% |

図にするなら「量の帯」と「コストの帯」を上下に並べて、幅が反転する様子を見せると伝わる。

---

## 10. 中断コスト（発見した現象）

```
作業中 ──────── 中断（1時間以上）──────── 再開
  │                                          │
  cache-read で安く回る                      1h キャッシュが失効
  1 通 $0.15〜0.35                           全量を書き直す
                                             1 通 $6.38（実測）
```

判定条件は `cache-read == 0 かつ cache-write >= 50,000`。
`ctm query` はこれを自動検出して「キャッシュ失効による再構築」として分離表示する。

実測では、ある 12 時間の作業でこれが **3 回・$15.65・全体の 25.2%** を占めていた。

## 11. 依存関係

```
外部依存: なし
ランタイム: 不要（Go の単一 exe・約 2.5 MB）
必要なもの: ~/.claude/projects が読めること
```

Go 標準ライブラリのみ。Python もサービス基盤も使わない。
